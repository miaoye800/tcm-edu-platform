01这个模块是什么

一句话：把教材里“谁和谁有什么关系”抽成机器可查的结构，做成一堆纯代码查询函数，供页面和智能体调用。

它不是“一张画给人看的图”。画布只是它的一个出口。真正的本体是四张 SQLite 表和九个查询函数——每条关系都带出处，每个查询都不调模型。

它替掉的是什么

以前问题现在
图谱是“要被生成的资源”，GraphAgent 现编 同一个主题两次生成结果不同，评审当场复现不了 图谱是服务，Agent 是调用方。结构层离线固化，查询层纯代码，只有表达层交给模型
1571 条边里 915 条（58%）是“同归经、同功效、同性味” 相似度是药材属性的函数，落库后必然与属性不同步，且占掉大半存储却答不了任何真实提问 相似度改为运行时计算（similar_neighbors），tier3_persisted: 0 作为自检位
知识树 117 个知识点对 76 味药，名字交集只有 24 个 前端拿树节点 id 查药，查不到 → 404 → 回落 15 个硬编码的假节点 实体对齐后 209 个 point 中 206 个挂上实体，悬空引用 0
十八反、剂量、毒性校验埋在画像流程里，靠关键词硬匹配 没有 API、没有页码、没有 edge_id，问“凭什么”答不上来 独立审查器，每条结论带 kind + 教材页码 + 原文
设计总原则 答案要唯一、可审计、可复现、离线、省钱 → 固化进结构；问题开放、要措辞、要多步推理 → 才交给模型。 这条线划错，后面所有取舍都会跟着错。

02数据模型

四张核心表，分工是“我是谁 / 我还叫什么 / 我和谁什么关系 / 这条关系凭什么”。

2.1 kg_entity —— 一个东西的身份

表里存的是“这个东西存在”，不是“这个内容的全文”。正文放在 payload_ref 指向的 JSON 文件里。

字段类型含义与约束
idTEXT PK主键。herb_mahuang / syndrome_<hash> / formula_<slug>。由名字稳定生成，改名字不会改 id。
kindTEXT实体种类，七值闭集：herb 药、syndrome 证候、formula 方剂、category 类属、meridian 归经、effect 功效、symptom 症状。后四种在 CHECK 里预留了位子，目前没有实体——归经与功效现在还是药材身上的属性数组。
nameTEXT正名，与 kind 组成唯一索引 kg_entity_kind_name。同名不同类可以共存（“补气”既可能是功效也可能是证候）。
pinyinTEXT全拼，用于检索与纠错（fuiing → fuling 这类历史拼写靠 _load_pinyin_fix 修正）。
canonical_idTEXT FK指向“正身”。别名实体、异名实体用得到，避免同一味药出现两个独立身份。
knowledge_node_idTEXT挂到知识树的哪个节点。这是实体与学习路径唯一的桥；为 NULL 表示不在树上（如方剂、多数证候）。
statusTEXT五值：orphan 教材没立条目 / draft 立了但字段没抽 / pending 待复核 / approved 可用 / rejected。当前 1694 approved + 14 orphan。
payload_refTEXT正文字典文件的路径，如 data/herbs/mahuang.json。只存路径不复制正文——JSON 是 source of truth。
extra_jsonTEXT不常用字段的兜底袋，避免为一个小字段加一列。
created_at / updated_atTEXTISO 时间戳，用于增量同步与审计。

2.2 kg_alias —— 它还能叫什么

字段含义
alias别名本身。与 entity_id 组成复合主键，同一个别名可以指向多个实体（“参”既可能指人参也可能指党参），解析时按 kind 优先。
entity_id指向 kg_entity。
source别名从哪来，四类：name 正名本身（1708）、preparation 炮制品前缀（48，如“炙麻黄”“蜜黄芪”）、herb.aliases 药材条目自带的别名（45）、textbook_alias 教材别名表（3）。来源必须记，否则分不清“教材说的”和“我们推的”。

2.3 kg_edge —— 一条关系

这是整个模块的核心表。UNIQUE(source_id, target_id, relation_type, label) 保证同一条关系不会重复入库；relation_type 刻意不加 CHECK——枚举演进由 constants.py 管，SQLite 没法 ALTER CHECK，加一个类型就得 DROP 整表。

字段类型含义
idINTEGER PK自增。这就是前端“依据”按钮背后的 edge_id，所有归因、路径、详情都靠它回溯。
source_idTEXT FK起点实体。方向有语义：药→方是“组成”，方→药则不是。
target_idTEXT FK终点实体。
relation_typeTEXT关系类型，12 值（见第 3 节）。决定 tier、方向性、是否对称，是唯一权威定义。
tierINTEGER 1/2/3可信层。1 硬约束、2 教材事实、3 相似（永不落库）。
labelTEXT人读短句，如“人参反藜芦”“麻黄发汗力强，桂枝发汗力缓”。前端不拼字符串，直接显示它。
evidence_jsonTEXT出处块：[{page, quote, ref}]。页码、原文、章节。空数组意味着这条边无法溯源——属于缺陷。
confidenceREAL0~1。T1 恒为 1.0（人工核过）；T2 实测均值 0.709、区间 0.6~0.97。用途是排序与截断，不是真假判断。
derivedINTEGER0 从教材直接抽取（2056 条），1 脚本反推（3456 条，如“证方链”由方剂组成药的主治倒推）。反推的置信度会被压低。
statusTEXTpending / approved / rejected。当前 5512 条全部 approved。
reviewed_by / reviewed_atTEXT谁在什么时候核的。T1 边必须有人签字。
meta_jsonTEXT扩展属性（如方剂是否 incomplete）。
最容易踩的坑 组成边的方向是“药 → 方”，不是“方 → 药”。 旧代码直接套“source 含 target”，念出来成了“人参含参附汤”，把成分当成了容器。 现在 ask.py 按实体种类判断方向再念，而不是依赖建边时的书写习惯。

2.4 为什么 JSON 是 source of truth

data/herbs/*.json      真人维护的药材专著     ← 唯一事实来源
data/formulas/*.json   方剂主数据
data/curated/*.json    十八反 / 十九畏 / 七情实例 / 症状别名
        ↓  build_kg.py 可重跑
kg_entity / kg_edge    SQLite 索引             ← 可随时删了重建

判据：人工签字的东西不能丢，机器算的东西随时可重建。 所以 reset_db() 清空五张 KG 表，但故意不清 herb_draft* 三张——那存的是“谁在什么时候看过哪味药”的签字记录，不是索引。索引重建十次，不该让审计痕迹消失。

03关系的类型与分层

分层不是为了“打分”，而是因为三类知识在决策里的性质完全不同。混在一起，调用方只能靠比字符串来判，那正是重构要消灭的做法。

层性质为什么单独一层
T1 硬约束 / 禁忌 错了就是教学事故。只能来自人工 curated 表——LLM 候选一律拒绝，因为模型一定会“补充”出不存在的反药。当前 80 条：十八反 68、十九畏 12。
T2 教材明文记载的事实 配伍、方剂组成、药证链、鉴别。可被引用、可被质疑、可翻页核对。当前 5432 条。
T3 按属性算出来的相似 不落库。它是药材属性的纯函数，落库必然与属性不同步。只用于召回扩展，不进图、不进证据链。

3.1 十二种关系类型（当前实测计数）

关系层方向条数含义与来源
十八反T1对称68配伍禁忌，教材 p128。人工 curated，禁改。
十九畏T1对称12与七情里的“相畏”不是一回事，教材 p128 明确警告过名称混用，故单列。
相须T2对称27性能功效相似、合用增效。教材七情实例，p124-125。
相使T2有向4主辅关系。方向携带语义：source 是主药。
相畏T2有向4source 的毒副作用被 target 抑制。
相杀T2有向7source 能消除 target 的毒副作用。A 畏 B ⟺ B 杀 A，两条都要建，方向相反。
相恶T2有向2source 的功效被 target 削弱。
配伍T2对称3531教材记载两药配伍应用，但没标具体七情类别。旧代码把这 217 条全打成“相须”，等于编造；现在诚实叫“配伍”。信息密度低，扩检索时排在最后。
组成T2有向67药 → 方。由药材条目的 formula_ref 反推，覆盖不全（平均每方 1.7 味）。
药证链T2有向1491药 → 证。教材“主治”字段的结构化。
证方链T2有向119证 → 方。由方剂组成药的主治倒推（derived=1），置信度低。
同类鉴别T2对称180教材写的鉴别句，如“麻黄发汗力强…桂枝发汗力缓…”。两药对比的结论优先取它。

3.2 对称与有向

这个区分不是洁癖。对称关系（相须、十八反、同类鉴别…）建库时只写一条，查询时双向匹配；如果两个方向都建，边数会翻倍，而且迟早出现“A→B 有、B→A 没有”的脏数据。有向关系（相使、相畏、相杀、相恶、组成、药证链、证方链）绝不能自动补反向——补了就是编造。

04九个查询能力

全部在 app/kg/ 下，零模型调用。每一个的输出都只取决于库里的数据，同样的输入永远同样的输出。

entities.resolve(query, db_path) → KgEntity | None
把任意写法解析成实体。所有查询的第一步。
解析顺序
entity.id → alias → name → 知识树节点名 → 旧图实体 id。逐级尝试，命中即返回。
为什么五级
同一味药有四种写法：herb_mahuang / 麻黄 / 炙麻黄 / d17.s1.p1。入口不归一，后面每一层都要各写一份兼容。
查不到
返回 None，不猜。上层负责说“教材未收录”。
traverse.neighbors(center_id, *, hops=1, tiers=(1,2), limit=60, db_path) → Subgraph
从中心实体 BFS 取局部子图。图谱首屏就是它。
hops
跳数，钳制在 1~3。每跳一次 SQL，深度 3 以内开销可忽略。
tiers
只走这些层。默认 (1,2)——T3 收不到，即使调用方传了 3 也会被剔掉。
limit
节点上限。超出时优先保留：中心 → 跳数近 → tier 硬 → 置信度高。truncated 标记是否截断，不静默丢弃。
traverse.shortest_path(from_id, to_id, *, max_hops=4, tiers=(1,2), db_path) → list[KgEdge]
两实体间最短关系链。回答“这两味药怎么扯上关系的”。
算法
BFS，等权。故意不按置信度加权：真实的“麻黄→细辛→小青龙汤”不该因为某条边置信度低就绕远路。
代价
等权只回答“最少几跳”，不回答“哪条最重要”。所以经常经甘草这类枢纽中转。
找不到
返回空列表，上层说“不是没关系，是教材没写这条关系”。
traverse.similar_neighbors(entity_id, *, limit=12, relation_types=None, db_path) → list[SimilarityHit]
T3 相似邻居。运行时算，从不落库。
打分
共享功效每个 0.35（最多取 2 个）、共享归经每个 0.20（最多 2 个）、性同且味有交集 0.25，上限 1.0。
用途
召回扩展、推荐“你可能还需要看”。不进证据链，因为它是算出来的，不是教材写的。
compare.compare(left_key, right_key, *, db_path) → dict
两药对比。七个维度逐项求交集与差集。
七维
四气 / 五味 / 归经 / 功效 / 主治 / 用量 / 毒性，顺序固定，表格列不会因数据缺失而跳动。
三组
每维给 only_left / only_right / shared。
为什么不用模型
差异是可枚举的。让模型写，它会把教材原话换个说法，既不可溯源，还可能把“桂枝发汗力缓”说反。
summary 优先级
有“同类鉴别”边就用教材原句，没有才用差异表拼。
compare.find_path(from_key, to_key, *, max_hops=4, db_path) → dict
最短链 + 每一步的教材引文 + 一句人读的话。
输出
hops、path[]（每步带 edge_id、relation_type、tier、evidence）、sentence（如 麻黄 -[同类鉴别]-> 桂枝）。
ask.ask(question, *, hops=1, limit=40, max_seeds=3, seed_ids=None, expand=True, db_path) → AskResult
问题 → 结构化答案。确定性模板拼装，不调模型。
种子
问题里抠实体名。按名字长度倒序 + 区间占用，避免“麻黄”从“麻黄汤”里被抠第二次，也避免“牵牛/牵牛子”被当成两个。
seed_ids
检索已经给出实体 id 时直接用，不再回头解析文本——那等于把检索白做了。
expand=False
对照模式：只认实体不扩图，用来证明“扩展这一步到底贡献了什么”。同一问题关掉扩展后，关系 0 条、原文 0 条。
prescription.review(payload, db_path, *, syndrome_hint=None) → ReviewResult
处方审查。纯规则 + 图遍历，同步、不调模型。
findings.kind
herb_normalized 药名归一、herb_not_structured 无结构化条目、dose_abnormal 剂量越界、toxic_misuse 毒性误用、toxicity_unknown 毒性未录、incompatible_pair 配伍禁忌、case_unresolved 证候解析不了、case_mismatch 证药不符、unrelated_herb 药与证无关、no_recognized_herb 未识别出药。
syndrome_hint
口语描述（“一咽口水就疼”）匹配不到时，先用模型在闭集里挑证候，再把结果从这里喂进来重跑。注意是“从候选里选”，不是“自由生成”。
reverse.reverse_lookup(target, *, top_k=3, db_path) → dict
症 → 证 → 方 → 药。三段全查表。
四级命中
name 证名原样命中（最可靠）→ alias 口语别名 → phrase 教材症状短语倒排（6262 条）→ fuzzy 字符二元组兜底（最弱）。
为什么 top_k=3
给 5 个以上，用户会以为“这些都是对的”，而实际只有第一两个有真实边支撑。
空结果
返回 ok:false + reason + hint（该怎么问）。绝不给“看着像”的证名——那个证一旦进处方审查，错的不是展示，是一次开方。
attribution.attribute_mistake(mistake_id, *, persist=True, db_path) → dict
错题归因。五类闭集，每条非 unknown 必须带 edge_id。
五类
概念混淆 / 禁忌错认 / 要点缺失 / 选错药 / unknown。
unknown 是一等公民
没有可用鉴别事实时，必须明说“归因不了”以及卡在哪一步（unknown_reason）。把“不知道”写成“概念混淆”，会骗老师补一个不存在的漏洞。
写入
先按 mistake_id 删干净再插。SQLite 里 NULL != NULL，edge_id 为空的 unknown 行靠 UNIQUE 去不了重。归因结果不写回 mistake_record——它是派生数据，重算即覆盖。

05HTTP 接口手册

路由集中在 app/api/kg.py，前缀 /api/kg。除 /health 外都需要登录，库路径通过 get_kg_db_path 依赖注入（测试可整体替换）。

端点方法参数与说明
/api/kg/healthGET无需鉴权。返回实体/边分层计数、tier3_persisted（必须 0）、dangling_links（必须 0）、herbs_with_monograph / herbs_draft / herbs_orphan 三类分开数、kg_ready。
/api/kg/searchGETq 关键词、kind 限定种类、limit。走名字与别名模糊匹配，给前端下拉框用。
/api/kg/askPOSTquestion、hops、expand、seed_ids。返回 answer + seeds + graph{nodes,edges} + citations。
/api/kg/prescription/reviewPOST处方 payload（患者描述 + 药味剂量）。返回 findings[] 与 refs[]。
/api/kg/neighbors/{center_id}GEThops 1~3、limit 5~120、tiers 逗号分隔（默认 1,2）。返回旧 GraphContent 结构 + meta，所以前端换端点不必改组件。解析不到时返回 200 + 单节点占位，不是 404。
/api/kg/entity/{entity_id}GET实体详情。边按 tier 分组：edges:{"1":[…],"2":[…]}，每条带 edge_id、direction（out/in）、peer、evidence。未知实体返回 404——与 neighbors 相反，因为空白药材卡会被读成“这味药没功效”。
/api/kg/reverseGETtarget 症状或证候名、top_k。返回候选证 + 药 + 方 + 每步 edge_id。
/api/kg/compareGETleft、right。返回 differences[]、textbook_differentiation、shared_relations[]、constraints[]、summary、两侧 source 出处。
/api/kg/pathGETfrom_id、to_id、max_hops。返回最短链。
/api/graph/{center_id}GET旧契约入口，内部同样走 KG 适配层。保留是为了让详情面板与 default-center 不受影响，观察期后下线。
两条接口的容错方向相反，这是故意的 neighbors 查不到返回 200 + “教材未收录”单节点：如果返 404，前端会回落到 15 个硬编码的假图。 entity 查不到返回 404：详情面板拿不到内容就该报错，渲染一张空卡等于说“这味药什么功效都没有”。

06构建流水线

三个脚本，顺序不能换，全部幂等可重跑。

# 1. 实体对齐：三套名单 → 1708 个实体
python scripts/kg_align.py [--dry-run]

# 2. 建边：T1 硬约束 + T2 事实关系（先清空再写，--keep 增量）
python scripts/build_kg.py [--dry-run] [--keep]

# 3. 前置顺序：父子层级 + 章节排序 + 环检测
python scripts/derive_prerequisites.py [--dry-run]

# 验收：T3 必须为 0，dangling 必须为 0
curl http://127.0.0.1:8000/api/kg/health

6.1 kg_align.py 的三条规矩

  • 不追求 orphan = 0。没有专著的药材显式标 orphan，前端显示“教材未收录”。编一个映射比留空更假。
  • 先清残留药材再 upsert。拼音/slug 校正会改 id（herb_fuilng → herb_fuling），不清就会留下两条同一味药。
  • 只写 kg_entity / kg_alias，不动 knowledge_node 与旧 herb_relation。对齐是加索引，不是搬家。

6.2 build_kg.py 的数据来源与可信度

层关系来源可信度
T1十八反 / 十九畏data/curated/incompatibility.json（人工，教材 p128）最高，禁改

6.3 derive_prerequisites.py 的四条规则

  1. 父子层级 → strict（必须按顺序学）
  2. 同章节按 sort_hint → free（可并行）
  3. 方剂组成依赖
  4. 证候依赖

order_sensitivity 是关键语义：strict 会让学习计划器锁住后一个节点，free 允许并行。所以脚本遇到已存在的边灵敏度不一致时只报冲突、不覆盖——改这个值等于改学习计划的排布方式，属于需要评审的迁移，不该由推导脚本顺手改掉。

07与智能体的关系

这是目前最需要说清楚的一块，因为它和直觉不一样。

7.1 现状：图被用到了，但不是“模型决定调用”

链路接入方式说明
对比页 / 图谱页 / 图谱问答 / 处方审查 / 错题归因页面直连用户点按钮，前端直接请求 /api/kg/*。模型不参与。
资源生成（doc / mindmap / ppt / graph / quiz / story）隐式retrieve_resource_docs() 里做的 GraphRAG，见下。
对话（/api/chat/stream，LangGraph）未接入只有 router → rag_agent / explain_agent / path_agent / profile_agent 四个节点，没有 kg 节点。所以聊到“麻黄和桂枝什么关系”现在不会走图谱。

7.2 GraphRAG：图是怎么进资源的

topic "麻黄为什么配桂枝"
  ↓ 向量召回 search(topic, top_k)
  ↓ 精确药名优先 _prioritize_exact_herb（题目点名的药必须进）
  ↓ 取种子：score ≥ kg_seed_threshold 且带 entity id
  ↓ 每个种子 neighbors(hops=1) 沿 T1/T2 补一跳
  ↓ 按关系优先级排序（相须 0 < 相使 1 < 同类鉴别 2 < … < 配伍 7）
  ↓ 只保留 data/herbs 里有专著的那些
  → 追加为 ResourceDoc，白名单随之扩大

三个刻意的约束：只补有专著的药（补进来也是空字段，模型只能编）；只补 ResourceDoc 不补裸药名（白名单从 docs 生成，补裸名会让白名单和正文脱节）；图坏了不影响检索（异常吞掉，扩展是加分项，不该把“查得到麻黄”也拖死）。

实测效果：问“麻黄”，召回从 5 味扩到 7 味，多出桂枝、柴胡。

7.3 如果要接成对话工具

两条路，取舍很明确：

方案做法代价
隐式对话前先跑一次 ask()，把结构化结果塞进上下文稳、可控，但每轮都付一次查询与 token，且模型不知道“我还能再查”
显式工具注册成 function calling 工具，模型自己决定调灵活，但必须加护栏：工具只返回结构化事实 + 引用，措辞交给模型。否则等于把唯一能保证可溯源的环节交出去了
接工具时最容易破的红线 模型拿到 neighbors 的结果后，很自然会“顺手总结一下”，于是多出一批图里没有的关系。 护栏写法：工具的返回值里每条关系都带 edge_id 与 evidence，下游校验时只允许引用这些 id；引用不到就删句，不删就报错。

08边界与缺口

下面每一条都是已知、有原因、暂时不该被当成 bug 修的。写在这里是为了让下一个人不要在同一个地方绕圈。

边界性质说明
方剂组成不全数据组成 边从药材条目反推，平均每方 1.7 味，data/formulas/_index.json 自标 incomplete=true。所以反查“咽喉肿痛”能到证和药，方是空的。补齐要走方剂抽取，不是查询写错了。
前置推导 R3/R4 产出 0 条数据端点是“方剂 / 证候的知识树节点”，而树只覆盖中药学 21 章的药材（209 个 point）。40 个方、1203 个证都没挂树，脚本如实报 blocked，不编端点凑数。
归经 / 功效 / 症状 暂无实体设计它们在 kind 的 CHECK 里，但现在是药材的属性数组。变成节点要先定“归脾经”这条边挂什么证据，是次数据改造。
15:00 后新增的边不自动生效运维边是离线构建的。data/herbs 改了不重跑 build_kg.py，图仍是旧的。没有增量触发器。
/api/graph/* 未下线过渡详情面板与 default-center 还在用，内部同走 KG 适配层。观察期结束后废弃。
T2 置信度是启发式设计0.6~0.97 的取值来自“字段结构化程度”，不是统计校准。只用于排序，不用于判真假。
口语覆盖仍不全数据症状词表 6262 条来自教材切分 + 少量人工别名（data/curated/symptom_aliases.json）。“嗓子疼”能到“咽喉肿痛”，“头昏脑涨得厉害”不一定。缺口由 symptom_llm.py 的闭集选择兜，不用自由生成。
