## 2. 三层分工的代码形状

```
plan_l1()
  ├── _l1_topological_plan()          内核：分层 + strict 边 → 题面（不是答案）
  ├── _request_plan_proposal()        模型：coverage / order / depth_overrides / rationale
  ├── validate_proposal()             内核：逐条验 → accepted | rejected[] → 重试 ≤2
  ├── _apply_verdict()                内核：把 include+order 变成 StagePlan[]
  └── verify_plan()                   原有：时间预算 / 考点覆盖 / 先修一致性
```

`_request_l1_preference` 被整个替换掉了。旧 prompt 只让模型**在 free 组内换顺序**
（"只能在free组内排序"），输出的 `ordered_domain_ids` 必须覆盖全部域——结构上就不
允许取舍。新 prompt 给的题面不变（拓扑底稿 / strict 边 / 打码画像 / 规划参数），
换掉的是**输出 schema**。

### 2.1 提案 schema

```json
{
  "coverage": {"include": ["general", "d01"], "exclude": [{"domain_id": "d10", "reason": "…"}]},
  "order": ["general", "d01"],
  "depth_overrides": {"d01": {"target_mastery": 0.9}, "d01.s1.p1": {"target_mastery": 0.95}},
  "resource_overrides": {"d02": {"resource_hint": "对比记忆"}},
  "rationale": [{"claim": "先攻克解表药", "basis": [{"dimension": "learning_goal", "value": "应试提分", "confidence": 0.9}]}],
  "confidence": 0.74
}
```

提案模型用 `extra="ignore"`，其余契约仍是 `extra="forbid"`：提案是**模型输出**，
多写一个键该被丢掉，不该让整次规划退回底稿。严格性用于"我们自己产出的结构"。

## 3. 八个拒收码

计划里列了 7 条，多出的一条 `proposal.unknown_target` 是兜底（模型编出不存在的
域/知识点 id）——没有它，这种幻觉只能整单作废或者静默放过。

| 码 | 触发 | 处置 | 实测 |
| --- | --- | --- | --- |
| `proposal.order_mismatch` | `order` 不是 `include` 的排列 | 整单拒 | ✅ |
| `proposal.strict_conflict` | strict 边倒置 / 层号回退 | 单条拒，按层重排 | ✅ |
| `proposal.missing_prereq` | 排掉的域是已选项的先修 | **自动补回** + 记 `auto_added` | ✅ |
| `proposal.exam_coverage` | 考点导向下整域跳过含 `≥0.8` 知识点的域 | 整单拒 | ✅ |
| `proposal.over_pruned` | 排除 `general` / 少于 `max(6, 60%×域数)` | 整单拒 | ✅ |
| `proposal.mastery_range` | `target_mastery ∉ [0.7, 0.95]` | 丢这一项、回落规则值 | ✅ |
| `proposal.untrusted_basis` | 理由引用 `confidence < 0.5` 的维度 | **保留决策、丢弃理由** | ✅ |
| `proposal.unknown_target` | 引用了图里没有的 id | 丢这一项 | ✅ |

三条值得单独说的判断：

**① 「层号不得回退」不能只查边。** 模型完全可以把第 1 层的域提到第 0 层前面，
而一条 strict 边都不碰。只校验边的话这条规矩等于空话，所以 `_repair_order` 同时
扫相邻对的层号；同一条错位被两种检法各抓一次时只报一次（否则用户以为模型犯了
两处错）。

**② 置信度比的是画像实测值，不是模型自报值。** 模型给 `basis.confidence` 写 0.99
也救不了一个 0.31 的薄弱点维度。有一条用例专门盯这个（`test_model_declared_confidence_cannot_outvote_the_profile`）。

**③ 整单拒才重试，且把拒收理由原样交回模型。** provider 挂了一次都不重试
（`test_giving_up_retries_exactly_max_times`）；重试只用于"提案不合法"，因为那是
模型能自己改的。用完 2 次仍不合法 → 规则底稿 + `fallback=True`。

## 4. 真实 19 域图上的实测

用 `scripts/seed_knowledge_tree.py` 的 19 域 / 117 知识点图跑一次完整协商：

```
domains 19   min_include 12   strict edges 18
hot 12 个：d01 d02 d03 d06 d07 d08 d11 d12 d13 d15 d17 d18
排除 d09 消食药 / d10 驱虫药 / d16 开窍药（三章低频）
→ stages 16，rejected []，fallback False
→ 第二次请求：versions [1]（未新增版本、未调模型）
→ input_hash 6a33386cf40a8c6a（两次重算一致）
```

### 4.1 踩到的坑：域级 `exam_frequency` 是占位值

第一版把域热度取成 `max(域自身, 后代知识点)`。真实数据里**每个域的
`exam_frequency` 一律是 0.8**（种子脚本的占位值），于是 19 个域全被判成热点，
考点导向下**任何**取舍都会被 `proposal.exam_coverage` 整单拒——跑出来的结果是
`fallback=True`、`auto_added` 一次都没触发过。取舍功能接了等于没接。

改成只看**后代知识点**（117 个点里 17 个 ≥0.8，散在 12 个域）之后，剩下 7 个域可裁。
这不是"放宽标准"，而是把规则从"容器标签"落到"真实考点"上——计划原文写的也是
「排除含 `exam_frequency ≥ 0.8` **点**的域」。

`test_hotness_comes_from_points_not_from_the_domain_placeholder` 用一对
刻意错位的数字（域 0.2 / 点 0.9）把这条钉住。

## 5. 逐点覆盖：L1 只排阶段，覆盖必须落库才活得到 L2

`planner.plan_l1()` 返回的 `PathPlan.nodes` 恒为空（知识点靠 `expand_domain` 懒展开）。
所以 `depth_overrides` **不能只存在内存里**——`create_l2_plan` 是另一次调用、另一次
`load_planning_context`。落点：L1 payload 的 `proposal.overrides`，L2 由
`plan_store.latest_l1_overrides()` 取回。

覆盖的优先级是**逐字段**的：点级 > 域级 > 规则值。

```
domains 19 图上的实测（d01 = 解表药）：
  depth_overrides {"d01.s1.p1": {"target_mastery": 0.93}, "d01": {"resource_hint": "对比记忆"}}
  → d01.s1.p1  target 0.93   （点级掌握度覆盖）
     d01.s1.p1  hint  对比记忆（域级资源继承）
     d01.s1.p2  hint  对比记忆（兄弟节点同样继承域级）
```

第一版写成 `overrides.get(node) or overrides.get(domain)` 整体取一个，结果点级只覆盖
掌握度时，资源会掉回规则值（"教材精读+要点笔记+测验"）——**点级覆盖把域级覆盖整个
盖掉了**。改成逐字段取 `_override_target(点级, 域级, 规则)` 才对。

## 6. 可复现的锚点：`input_hash` 的边界

`build_input_snapshot()` 装三样：七维（值 + 置信度）、`planning_params` + `time_budget`、
知识树指纹（`node_count` / `domain_count` / `edge_count` / `edge_hash`）。

刻意**不含**两样：

| 不含 | 原因 |
| --- | --- |
| **掌握度 / 进度** | 进度变了不该逼着重新问模型要取舍，那是 L3 `adjust_after_node` 的活 |
| **`user_id`** | 两个画像完全一致的用户算出同一个 hash 是**对的**；把 id 塞进去只会让"同一份输入"看起来不同，破坏 A/B。复用查询本身按 `user_id` 过滤 |

复用规则（`plan_store.find_reusable_l1`）：同 `(user_id, input_hash)` 命中
**非 fallback** 的 L1 直接返回原版号，不再调模型。底稿不复用——那是"模型没给成"的
产物，下次该重新问，不该被永久固化。

`temperature` 锁 0 只是让模型尽量稳定；**真正保证"同画像同计划"的是复用，不是采样配置**。

用户主动「重新规划」走 `PlanRequest.replan=True`（`reuse=False`）：他要新草稿，
不是旧版本原样返还。这条已在接口上留好，P5 的向导直接用。

## 7. 三样落库

`user_path_plan.payload_json` 里现在有（`payload keys` 实测）：

```
fallback / stages / nodes / suggestion / verify_attempts / verification_issues
+ proposal       提案原文 + accepted + include + auto_added[] + rejected[] + overrides[]
+ model_meta     {model, temperature: 0, prompt_hash, input_hash}
+ input_snapshot 七维 + 规划参数 + knowledge_graph{node_count, domain_count, edge_count, edge_hash}
```

没有这三样，**解释**（"凭什么给我砍了三章"）、**复现**（演示/回归/投诉）、**A/B** 三件事
一件都做不到。`PlanResponse` 也同步加了这三个可选字段（前端契约向后兼容）。

## 8. 向后兼容

旧 prompt 的输出形状 `{ordered_domain_ids, suggestion}` 仍然能被解析
（`PlanProposal.parse` 里做归一：等于"全量覆盖 + 模型排序"）。理由：录制回放
（`LLM_MODE=replay`）里还留着旧响应，一次换 schema 就全废太不值。

`test_llm_strict_edge_violation_is_rejected_to_topological_order` 随之改了断言：
以前整单退回底稿、建议文案是"当前按先修拓扑稳妥推进"；现在**单条拒 + 说清楚修了什么**——
"学习目标0.9→违规提前解表药；1 处顺序违反先修边，已按拓扑修正"。用户看到的是自己
同意过的取舍，加上一句"这里被内核按拓扑改掉了"。

## 10. 已知遗留

1. **域级热度依赖知识点频率的真实性**。现在 `data` 里 117 个知识点的 `exam_frequency`
   是 P1 造的合理值，不是真题统计。真要做"考点导向"的取舍，这列得有一份真实来源
   （真题分布 / 教材标注），否则取舍依据只是"看起来像"。
2. **`general` 域在种子里 `exam_frequency=1.0`**，但热度口径改成只看知识点后它不再是
   "热点"——它靠"必学"这条硬约束保底，不靠热度。两套机制别混。
3. **重试没有把失败样本单独记账**。`proposal.rejected` 只存最后一次的拒收记录；
   要看"模型老在哪条规则上翻车"，得把每一轮的 rejected 都留下（P5 做草稿版本时顺带存）。
4. **前端还没展示提案**。"砍了哪三章、为什么"目前只有 payload 里有，UI 上是
   `suggestion` 一句话。P5 的两段式向导是它的正式落点。
