## 2. 性能：唯一没过门的一条，且原因要说清楚

| 环境 | 数字 | 说明 |
| --- | --- | --- |
| headless Chrome + **SwiftShader 软件渲染** | **3–5 fps** | 835.6k 三角面 + bloom，纯 CPU 光栅化，不代表真机 |
| 用户开发机（真 GPU，Windows Chrome，Bloom 开） | **60 fps · 100 draw calls · 83.5 万面** | 第一份真实 GPU 数据，见下方「怎么读」 |
| 中端手机 / 教室机 | **未测** | 第 7 条的验收对象，仍未覆盖 |

### 2.1 这三个数怎么读

页面顶部那行 `60 fps · 最差帧 58 fps · 100 draw calls · 几何 835.6k 面`：

| 指标 | 含义 | 阈值判断 |
| --- | --- | --- |
| **fps** | 每秒出图数，被显示器 vsync **封顶** | 60 只说明"没掉帧"，**看不出余量**——好机器和刚够用的机器都显示 60 |
| **最差帧** | 统计窗口（0.6 s）内最长一帧换算的 fps | **真正该看的数**。≥50 说明拖动不顿；30–50 能撑但没余量；<30 必须优化 |
| **draw calls** | 每帧向 GPU 提交的绘制批次，CPU 侧开销 | 100 很低（3A 游戏常 1000+），合批有效。移动端 <150 安全 |
| **几何面数** | 三角形总量，GPU 侧开销 | 835.6k 桌面无压力；**手机 GPU 才是这里的风险点** |

⚠️ 三个容易被误读的地方：

1. **60 fps 不等于通过。** 它只是 vsync 上限。要判断余量，看"最差帧"，并且**在旋转/平移进行中**看，不要静止看。
2. **100 draw calls 是当前状态，不是上线状态。** 现在只点亮 4 个穴位、1 条经；26 条经的 Line2 是逐条提交的（主线 + 外晕 = 2 call/条），已通段也是逐段 2 call。全量时应重测，预计 200+。
3. **像素量敏感的只有 bloom。** UnrealBloomPass 是 3 个全屏 pass，开销与画面面积成正比，与面数无关。**把窗口拉到 2560 宽再读一次**，那才接近 2K 屏用户的真实情况；面数和 draw calls 不会因为窗口变大而变，fps 会。

**所以第 7 条现在是「桌面真 GPU 已过、移动端未测」。** 中端手机 ≥30 fps 这一条仍未验证，P3 开工前还得在目标设备上跑。

已知可降的手段（按性价比排），P3 必须做完再谈上线：

1. **只加载当前经 + 邻近区**（现在是 15 个 chunk 全下 67 MB）
2. **bloom 降分辨率或关掉改 billboard 假发光**（全屏 pass，最贵，且它是唯一吃满屏像素的）
3. **肌肉减面**：656k → 200k 级别（quadric 简化，atlas 原始已是 0.002 相对误差）
4. `setPixelRatio(min(dpr, 2))`，移动端降到 1
5. 资产走 gz（仓库自带 `.gz`，33 MB）+ Draco/meshopt

## 3. 实测踩到的 9 个坑（P3 直接照抄，不要重踩）

### 3.1 BodyParts3D **没有 UV** —— 肌理只能程序化

`atlas.json` 的 part 只有 `positions / normals / indices` 三个字段，**没有 uv**。
P0 的解法（已跑通，可直接搬到 P3）：

| 层 | 做法 |
| --- | --- |
| 分块 | 每顶点写 `aPart` 属性 + 随机明度顶点色，**merge 之后必须还在**（否则合并即变成一坨肉色） |
| 纤维 | `onBeforeCompile` 注入 triplanar 值噪声，**沿身体长轴把噪声拉长 7 倍**（不拉伸就是噪点不是纤维） |
| 起伏 | 噪声梯度投影到切平面扰动 `normal` |

实测参数：`uScale 58 / uAniso 7 / uBump 0.62 / uTint 0.20`。低于这个量级基本看不出来。

### 3.2 二进制格式（很容易读错）

```
position : Float32 × 3 / 顶点，字节偏移 = part.positions
normal   : Int16   × 3 / 顶点，normalized = true，字节偏移 = part.normals
index    : Uint32  × 1，字节偏移 = part.indices
```
`normal` 不是 float32 而是**归一化 int16**（省一半内存），`index` 是 uint32。
三个偏移都必须内存对齐，否则 `new Float32Array(buf, offset, len)` 直接抛错。

### 3.3 左右是两套实例，但进度只能算一份

经脉是 **26 条路径**（12 经 × 左右 + 任督中线），穴位 **670 个实例**（362 穴，中线单份）。
`meridian-surface.json` 的 key 形如 `LU1:1` / `LU1:-1`，后缀是左右符号。

→ 渲染两个光点，但**挂载小节与进度必须按 `(channel_id, code)` 归并**，否则会出现"左边学了右边没学"。

### 3.4 相机 tween 不能用 `dt` 累加

最初写 `camTween.t += dt / dur`，实测 1.9 秒只走了 0.4%，相机像没动。
改成 `performance.now()` 绝对时间后一次就对。

**教训**：动画进度一律用真实时间，不要累加帧间隔。

### 3.5 已通段不能按"路径采样点索引差"判连续

相邻两个穴位在路径上可能隔几十个采样点。最初用 `idx 差 ≤ 3` 判相邻，结果每段只剩 1 个点，`learnedSegments` 常年是 0。

正确做法：把该经**所有**穴位映到路径索引上排序，看**穴序列**里相邻两个是否都已学，再切这两点之间的路径。

### 3.6 raycast 打不中穴位，必须屏幕空间吸附

3 m 视距下穴位球只有 2–3 px。实测点"天府"（LU3）命中了"消泺"（TE12）——射线穿过前面的邻经穴位。

改成：投影所有穴位到屏幕，取 **24 px 内最近的、且法线朝向相机的**。命中率 100%，且不会点到背面。

### 3.7 CSS2DObject 不参与深度测试

转到背面时，正面的穴名会"透过身体"显示出来，比不显示更糟。
解法：每个标签存穴位体表法线，`normal · (相机 - 目标) < 0.06` 就隐藏。

### 3.8 `EffectComposer` 会重置 `renderer.info`

接上 bloom 后，右上角一直显示 `1 tris · 1 calls`——那是最后一个全屏 pass 的数字。
解法：`renderer.info.autoReset = false`，每帧开头手动 `reset()`。

### 3.9 fps 不能用"累加 dt"算

`frames / Σdt` 在 headless 被节流时会显示 17–22 fps，实际只有 3 fps。
必须用 `frames / (真实经过秒数)`。**这条差点让我误判性能通过。**

### 3.10 OrbitControls 里「PAN + 按着 shift」会被翻成旋转

想加"Shift+左键平移"时，最直觉的写法是把 `controls.mouseButtons.LEFT` 临时改成 `MOUSE.PAN`。
**没用**——它内部有这么一段：

```js
case MOUSE.PAN:
  if (event.ctrlKey || event.metaKey || event.shiftKey) { handleMouseDownRotate(...); }  // 反过来变旋转
```

改常数等于喂给它一个自相矛盾的组合，最后还是转视角（而且 target 一动不动，很容易误以为"平移没写对"）。

解法：在 `pointerdown` 的**捕获阶段**用 `stopImmediatePropagation()` 把它整个截走，自己算位移。
注意必须是 `stopImmediatePropagation` 而不是 `stopPropagation`——两者在**同一个元素**上的其他监听器面前，
只有前者能拦住。

另外记得 `contextmenu` 要 `preventDefault()`，否则右键一按就弹菜单，右键平移没法用。

### 3.11 键盘/拖动速度不能按"每帧多少像素"算

第一版键盘平移写的是 `每帧 6px`。headless 3 fps 下等于 18 px/s，按一秒几乎没动；真机 60 fps 又变成 360 px/s。
改成 `像素/秒 × dt` 才与帧率无关。

鼠标拖动没这个问题——`OrbitControls` 用的是事件里的 `clientX/clientY` 差值，天然按位移而不是按帧。
自己的 `panCamera()` 同理，所以 Shift 拖动在任何帧率下手感一致。

3 fps 是软件渲染的假象，不能当结论，但"835k 面 + bloom"这套组合在移动端仍有风险，不能因为桌面 60 就跳过这一步。
