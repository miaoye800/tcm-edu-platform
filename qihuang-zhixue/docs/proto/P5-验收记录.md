## 2. 为什么是 `status='draft'`，不是 `plan_kind='draft'`

第一版实现把草稿当成新的 `plan_kind` 值，跑测试直接撞 SQLite 的 CHECK 约束。
SQLite **不支持修改 CHECK**，要改只能走「建新表 → 搬数据 → 删旧表 → 改名」那 12 步，
而这张表里存着所有历史版本。

改成在 `user_path_plan` 上补四列：

```sql
ALTER TABLE user_path_plan ADD COLUMN status TEXT NOT NULL DEFAULT 'active';
ALTER TABLE user_path_plan ADD COLUMN stage TEXT NOT NULL DEFAULT '';
ALTER TABLE user_path_plan ADD COLUMN parent_version INTEGER;
ALTER TABLE user_path_plan ADD COLUMN confirmed_at TEXT;
```

`_ensure_columns()` 先 `PRAGMA table_info` 查已有列再逐列 `ADD`，老库直接兼容
（`CREATE TABLE IF NOT EXISTS` 不会补列，这是踩过的坑）。

**确认 = 追加一条新行**（`status='active'`, `parent_version=草稿版号`），
草稿行永不 UPDATE。这样"这份计划是怎么来的"永远可回溯，而"当前生效的是哪一版"
只是一次 `WHERE status='active' ORDER BY version DESC LIMIT 1`。

## 3. 六个端点

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| POST | `/api/path/plan/draft` | 出骨架草稿（可复用同 `input_hash` 的既有 L1） |
| GET | `/api/path/plan/draft` | 取当前未确认草稿（重进向导接着改） |
| PATCH | `/api/path/plan/draft/{version}` | 应用编辑（8 种 op），只追加 draft 行 |
| POST | `/api/path/plan/draft/{version}/confirm` | 确认骨架 → 追加 active 行 |
| POST | `/api/path/detail/draft` | 骨架确认后展开逐点明细（一次最多 4 个域） |
| POST | `/api/path/detail/draft/{version}/confirm` | 确认明细 → 追加 l1 + 每域一条 l2 + 播种子状态 |

编辑 op 共 8 个：`reorder` / `remove` / `include` / `set_domain` / `set_node` /
`drop_node` / `restore_node` / `set_budget`。

**为什么编辑不复用已有的 `reorder` / `defer`**：那三个直接写 `user_path_state`。
草稿阶段一旦调它们，用户取消后地图上会留一片幽灵点位——学过的没学过混在一起，
而"确认"这个动作就失去了意义。

## 4. 「确认过的草稿还算待确认」

确认只**追加** active 行，草稿行仍是 `draft`。于是 `latest_draft()` 会把刚确认过的那份
当成"最新草稿"返回，用户重进向导看到自己刚确认的取舍还在待确认状态，以为没点上。

修法是让 `latest_draft` 认人：

```python
confirmed = {int(item["parent_version"]) for item in items
             if item["status"] == "active" and item["parent_version"] is not None}
for item in reversed(items):
    if item["status"] != "draft" or item["version"] in confirmed:
        continue
```

## 5. 冻结重排：`_ordered_points(frozen=…)`

已学过的点是资产。局部重排不许把它们往前挪或往后推——用户会看到自己学过的关
被移到还没学的地方。

```python
for source, target in self._effective_point_edges(selected, sensitivity=sensitivity):
    if source in frozen_set or target in frozen_set:
        continue          # 已学 = 已满足的前驱，它参与的边不再约束新顺序
    projected.append({...})
```

`replan()` 只改 `seq`，**绝不改 `section_id`**：穴位归属是造图时定的，重排改它等于
把知识点搬到别的穴位上。

## 6. `excluded[]` 的候选集不能拿"最终留下的域"反推

被砍掉的方向**不在**最终域集合里，反推得到的是空集，于是"跳过了 3 章（可以加回）"
永远是空的，一键加回也就永远不可用。

正确来源是取舍边界里的全集减去最终域：

```python
scope = proposal_scope().domain_ids          # 取舍边界内所有域
excluded = [d for d in scope if d not in included]
```

## 7. 跨域 `seq` 必须重排成全局连续

`expand_domain` 返回的 `seq` 是**域内**序号，每个域都从 1 开始。明细草稿跨域拼接后
出现四个 `seq=1`，而 `_next_node_id` 是靠 `(stage, seq)` 找下一关的——它会跳过整个
方向，表现为"学完这一关，下一关不出现"。

```python
for index, node in enumerate(nodes, 1):
    node["seq"] = index
```

## 8. 前端：四步 + 409 + 谁来关窗

```
① 说目标   自由文本 → POST /plan/draft
② 定取舍   上移/下移/跳过（PATCH reorder/remove）+ excluded 一键加回（PATCH include）
③ 看细节   逐点目标掌握度（el-input-number 0.70–0.95）+ 略过
④ 确认     路线已生效 / 去地图上看
```

`guard()` 统一接异常：409 时 `notice.value = message`，**草稿不变**。这里必须"什么都
不变，只多一句话"——把用户改了一半的列表留下，他会以为自己改成功了。

**关窗的时机**：第一版 `@confirmed` 里顺手把 `planVisible=false`，结果第 ④ 步永远
不显示——用户点完一个需要读两分钟的确认动作，界面直接弹回地图。现在关窗只由向导里的
「去地图上看」触发，父级只负责 `path.load()`。

## 9. 实拍记录：这一轮逮到三个只有真数据才会暴露的缺陷

实拍脚本 `frontend/scripts/capture-plan-wizard.mjs` 走真后端（不是 mock），
预置账号登录后连点五个按钮。第一次跑到第 ② 步就卡住，逐个查下去：

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 点「就用这个顺序」后红字、明细永远出不来 | `topo_sort` 遇到"free 边与 strict 边打架"直接 `raise ValueError`，端点 500 | free 只是"可以并行"的提示，冲突时丢提示、保严格序（`_FreeHintConflict` + 二次分层）。回归用例 `test_topo_sort_drops_free_hints_that_contradict_strict_order` |
| 2 | 修完 1 还是 500 | `attach.connect()` 没开 `row_factory`，`dict(row)` 拿 18 列的 tuple 当键值对解 | `conn.row_factory = sqlite3.Row`。**这个模块此前一个测试都没有**，单测里 `map_*` 表是空的，循环一次都没进去，所以一路绿灯。新增 `tests/test_meridian_attach.py`（4 项，造真行） |
| 3 | 明细列表显示 `b01.s1.p1` 这样的 id | `NodePlan` 只带 id，没有 name | `create_detail_draft` 从 `context.knowledge_nodes` 补 `name`；用例断言每个点都有 name |
| 4 | 确认完对话框自己关了 | 父级 `@confirmed` 里关窗 | 关窗交给向导 |

第 3 条不是崩溃，但影响更坏：用户要确认的是一屏编号，他没法判断该砍哪一条。
