## A. 浏览器里点（9 项）

### A1. 图谱首屏能出图 ⭐ 本轮修复

- **入口**：左侧栏「图谱 → 中药图谱」，或 http://127.0.0.1:5173/atlas
- **操作**：打开即可
- **✅ 改后**：画布中央「人参」，四周散开 党参 / 白术 / 茯苓 / 附子 / 黄芪 / 麦冬 / 五灵脂 / 四君子汤 / 参附汤 / 莱菔子 / 肺气虚弱 / 气虚欲脱·肢冷脉微 / 津伤口渴内热消渴 / 心神不安 等 28 个节点、34 条连线
- **❌ 改前**：统计数字照常显示「28 个节点 / 34 条关系」，画布**一片空白**
- **判失败**：有数字没图 → F12 Console 找 `Three-dimensional knowledge map could not start`（多半是浏览器禁了 WebGL，换 Chrome）

### A2. 图谱中心是「药材」不是「总论」 ⭐ 本轮修复

- **入口**：同上 `/atlas`，看标题第一个词
- **✅ 改后**：**人参**
- **❌ 改前**：`性味归经 · 关系图谱`，画布只有孤零零 1 个点、0 条线
- **为什么**：你的进度停在总论 `general.p1`（性味归经），旧代码直接拿它当中心。现在「当前节点出不了图，就退到关系最多的那味药」。

### A3. 点节点看详情（含教材原文）

- **入口**：`/atlas` → 点画布上的「**人参**」节点
- **✅ 改后**（实测内容）：
  - 头部：`草 / 药材 / 人参 / 补虚药·补气药`
  - 性味归经：`性微温，味甘、微苦，归脾、肺、心、肾经。`
  - 功效主治：`大补元气；复脉固脱；补脾益肺；生津养血；安神益智；气虚欲脱，肢冷脉微：…（带教材原文段落）`
  - 常用剂量与炮制：`3~9g；另煎兑服；用于急救虚脱可用15~30g`
  - 使用禁忌：`实证、热证而正气不虚者忌用；不宜与藜芦同用`
- **❌ 改前**：只有一句模糊描述，没有剂量、没有禁忌
- **判失败**：面板一直「加载中」、或 404

### A4. 详情面板不再显示 `[object Object]` / 裸 JSON ⭐ 本轮修复

- **入口**：同 A3 的详情面板
- **✅ 改后**：剂量行是可读中文（见上）
- **❌ 改前**：剂量行显示 `[object Object] 知识库暂未覆盖`；主治一栏直接糊出 `{"syndrome":"气虚欲脱，肢冷脉微","description":"本品甘温补虚…"}`
- **根因**：后端 `常用剂量与炮制.剂量` 是对象 `{text, min_g, max_g, usage_notes}`，前端类型却写成 `string`，插值就成了 `[object Object]`
- **判失败**：面板里能看到 `[object Object]` 或 `"syndrome"` 字样

### A5. 未收录的药材不再假装有图

- **入口**：http://127.0.0.1:8000/docs → `GET /api/graph/{center_id}` → 填 `not-a-real-node` → Execute
- **✅ 改后**：HTTP **200**，`nodes` 只有 1 个且 `brief` 为「**教材未收录**」，`edges: []`
- **❌ 改前**：返回 **404** → 前端收到失败就回落 `mockMahuangGraph`（15 个硬编码节点），你看到的「麻黄图」就是这么来的
- **红线**：「不知道」必须显式说出来，不能拿假数据顶上

### A6. 两药对比（不调大模型）

- **入口**：左侧栏「图谱 → 两药对比」，或 http://127.0.0.1:5173/compare
- **操作（最快）**：点「常用」那排的第一个按钮「**麻黄 / 桂枝**」
- **操作（手动）**：左框输「麻黄」→ 选「麻黄 药」；右框输「桂枝」→ 选「桂枝 药」；**然后必须点「开始对比」按钮**（不点不会出结果）
- **✅ 改后**（实测内容）：
  - 「教材原文 / 鉴别要点」：*麻黄发汗力强，兼宣肺平喘、利水消肿；桂枝发汗力缓，兼温通经脉、助阳化气* —— 出处《中药学》(钟赣生·新世纪第四版)·第八章·发散风寒药·麻黄
  - 「逐项差异」表格：五味（微苦、辛 vs 辛、甘）｜归经（肺、膀胱 vs 心、肺、膀胱）｜功效（发汗解表、宣肺平喘、利水消肿 vs 发汗解肌、温通经脉、助阳化气、平冲降逆）｜主治｜用量｜毒性
- **❌ 改前**：这个页面**不存在**
- **关键**：全程**没有 AI 生成等待**——差异是从药材 JSON 枚举的，鉴别句是教材原文

### B1. 处方审查：十八反拦截

`POST /api/kg/prescription/review` → Request body：

```json
{"prescription": "人参9g，藜芦3g"}
```

- **✅ 期望**：`"verdict": "block"`；`findings[0]`：`kind: incompatible_pair`、`reason: "藜芦 与 人参 属十八反，不可同方"`、`evidence[0].page: 128`、引文「藜芦反人参、西洋参、党参…」

- **❌ 改前**：没有这个接口

### B2. 处方审查：正常方子放行

```json
{"prescription": "金银花15g，连翘15g", "symptoms": "咽痛"}
```

- **✅ 期望**：`verdict` 为 `pass` 或 `warn`，**不会** block
- **注意**：`symptoms` 是**字符串**，传数组会 422

### B3. 关系路径：两味药怎么扯上关系

## H. P7 · 前端图谱改走 /api/kg（本轮补齐）

> 方案原文只允许改一个文件：`frontend/src/services/graphApi.ts`。
> 验收的核心不是「页面能看」，而是「改了端点之后，组件一行都没动」。

### H0. 审核结论

P0–P6 事前几轮已交付；P7 之前**没做**（`graphApi.ts` 仍指向 `/api/graph/{center_id}`，
而 `/api/kg/neighbors` 这个端点根本不存在——方案的 §3.5 里写了，代码里没有）。
P8 属于方案标注的可选项，本轮补齐了缺的那一项（按 tier 分组筛选）。
顺带补了 §3.5 表里另外两条只存在于文档的接口：`/api/kg/entity/{id}`、`/api/kg/reverse`。

### H1. 图谱首屏走新端点（浏览器）

- **入口**：http://127.0.0.1:5173/atlas
- **操作**：F12 → Network → 过滤 `neighbors` → 刷新页面
- **✅ 现在**：请求是 `GET /api/kg/neighbors/d17.s1.p1?hops=...`，返回 JSON 顶层有
  `center_id / nodes / edges / sources`，外加一个 `meta: { using_mock: false, center_resolved: true, tier_counts: {...} }`
- **❌ 改造前**：请求是 `GET /api/graph/d17.s1.p1`
- **判失败**：网络面板里还能看到 `/api/graph/` + 中文 id 的请求（说明前端没换过去）；
  或 `meta.using_mock` 是 `true`（那说明掉落到了 15 个硬编码节点的 mock）

### H2. 按 tier 分组筛选（本轮新增，唯一可见的新控件）

- **入口**：同 `/atlas`，标题下方筛选区，第三行「层级」
- **操作**：点「T2 教材事实」把它关掉，只留「T1 硬约束」
- **✅ 现在**：画布上的连线大幅减少，只剩禁忌类关系。实测「人参」：默认 T1+T2 共 74 条边，
  只留 T1 后剩 **2 条**（十八反·藜芦、十九畏·五灵脂）
- **为什么这个开关有意义**：T1 是「不能一起开」的硬约束，T2 是「教材写过的配伍事实」。
  它们不是「置信度高低」的排序，而是两种不同性质的知识。关掉 T2 之后剩下的那几条线，
  就应该全是不能碰的组合——如果里面混进了「同类鉴别」，说明分层写错了
- **判失败**：关了 T2 画布还是满的（筛选没进 `visible` 计算，只是加了个按钮）；
  或角标数字和实际边数对不上

### H3. 中心节点不存在时仍然不 404（回归项）

- **入口**：http://127.0.0.1:8000/docs → `GET /api/kg/neighbors/not-a-real-node` → Execute
- **✅ 现在**：HTTP 200，`nodes` 只有 1 个，`brief` 是「教材未收录」，`edges: []`，
  `meta.center_resolved: false`
- **❌ 若返回 404**：前端 `stores/graph.ts` 会回落 mock，用户看到一张麻黄假图

### H4. 章节节点 / 总论知识点不再被当成药材（本轮修）

- **入口**：`GET /api/kg/neighbors/d01`（解表药，章节节点）、`GET /api/kg/neighbors/general.p1`（性味归经）
- **✅ 现在**：`type` 是 `category`（类属），`brief` 是「章节节点·暂无图谱关系」/「总论知识点·暂无图谱关系」
- **❌ 改造前**：`kind_of()` 对不认识的 id 一律返回 `herb`，于是「性味归经」顶着**药材**的字段表
  出现在详情面板里——把概念说成药，比缺失更误导

### H5. 实体详情：边按 tier 分组（新接口）

- **入口**：http://127.0.0.1:8000/docs → `GET /api/kg/entity/herb_renshen`
- **✅ 现在**：`edges` 是 `{"1": [...], "2": [...]}` 两组，每条带 `edge_id` / `direction`（`out` 还是 `in`）/
  `peer` / `evidence`；`edge_counts` 给两组的条数（人参：T1 2 条、T2 99 条）
- **为什么分组**：`同类鉴别` 和 `十八反` 在界面上长得一样，但在决策里差一个数量级。
  平铺返回等于把「怎么判」推给调用方去比字符串——那正是重构要消灭的做法
- **判失败**：`edges` 是一维数组（没分组）；或某条边没有 `evidence`

### H6. 反向检索：症 → 证 → 方 → 药（新接口 + 新面板）

- **入口（界面）**：http://127.0.0.1:5173/kg-ask ，第二张卡「从一个症状往回找」
- **操作**：点示例「气虚欲脱」→ 反查
- **✅ 现在**：命中的证候（证名命中）、它下面的药（走 `药证链`）、常用方（走 `证方链`，
  括号里是方的组成）。命中层级标在证名左边：`证名命中 / 别名 / 症状短语 / 字面近似`
- **❌ 改造前**：这个能力在方案 §0 里是四类必答问题之一，但前后端都没有入口
- **故意不给模型兜底**：口语说法是开放的（「嗓子疼」），教材词表是封闭的（「咽喉肿痛」），
  缺口永远补不完。模型遇到缺口不会说「不知道」，它会就近编一个证。
  那个证一旦进到处方审查，错的不是一条展示，是一次开方
- **判失败**：随便输一句「zzzz」却能返回一批证名（那就是在编）；
  正确表现是明说「教材词表里没有能对上「zzzz」的症状或证候」并给一句「怎么说才对」

### H7. 三条已知边界（P7/P8 相关）

- **`/api/graph/*` 没删**：它仍是「旧前端契约」的入口，内部同样走 KG 适配层。
  保留是为了让还没改的页面（详情面板、默认中心）不受影响；等 P7 的观察期过了再下线。
- **方剂组成普遍不全**：`组成` 边是从药材 monograph 的 `formula_ref` 反推的（平均每个方只有 1.7 味），
  `data/formulas/_index.json` 自己也标了 `incomplete=true`。所以反查里「方 → 药」这一步经常只列出 1-2 味，
  这是数据覆盖问题，不是查询写错了。补齐需要 P4 的方剂抽取，不在本轮范围。
- **`/atlas` 的 tier 角标是本次请求内的计数**：`hops=1`、`limit=40` 的窗口内统计，
  不是全库 5512 条边。想知道全库数字看 `/api/kg/health`。
